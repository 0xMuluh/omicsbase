# Report Writing Guide

Use this guide for Quarto reports, analysis scripts, READMEs, and planning documents generated by OmicsBase.

## Core Rule

Write like a careful analyst, not like a chatbot. Every sentence, heading, table, and comment should help the reader understand the study, the data, the model, or the decision.

## Avoid Useless Comments

Do not add comments that restate the next line of code.

Bad:

```r
# Load data
data <- readRDS("data/processed.rds")

# Create table
make_table(tbl)
```

Better:

```r
data <- readRDS("data/processed.rds")
make_table(tbl)
```

Use comments only when they preserve a decision that is not obvious from the code.

Good:

```r
# Premature is SPSS-coded as 2 = yes in the current clinical file.
is_premature <- !is.na(Premature) & Premature == 2
```

## Avoid Unnecessary Name References

Do not put analyst names, project-owner names, lab nicknames, or helper-name vanity labels into report text, function names, titles, or variables unless they are part of a real dataset path or necessary provenance.

Bad:

```r
lab_cohort_data <- extract_lab_cohort_data(...)
```

Better:

```r
analysis_data <- extract_analysis_data(...)
```

Bad:

```yaml
website:
  title: "Internal nickname - Person's Project"
```

Better:

```yaml
website:
  title: "IBD microbiome analysis"
```

## Avoid Meta-Commentary

Reports should not describe our workflow unless it is scientifically relevant.

Bad:

> This site is currently scoped to the study overview and does not yet report results.

Better:

Omit it. The navigation and available pages already show the scope.

## Avoid AI Drivel

Do not use filler, apologies, motivational language, or generic explanation.

Bad:

> This comprehensive and robust report provides valuable insights into the fascinating relationship between the microbiome and disease phenotype.

Better:

> This report specifies the differential abundance panels, covariate blocks, and planned model families.

## Prefer Compact Scientific Structure

Use short headings and table-driven specification.

Use sentence-style headings by default. Do not title-case or camel-case every heading.

Bad:

```markdown
## Covariate Selection Framework
## Planned Complete-Case Availability
## Purposeful Selection Decision Support
```

Better:

```markdown
## Covariate selection framework
## Complete-case availability
## Decision support
```

Keep capitalization for proper nouns, acronyms, model names, and established labels such as `PERMANOVA`, `ANCOM-BC`, `PCA`, `VIF`, `TSE`, and `FDR`.

Good section rhythm:

1. Analysis question
2. Data and filtering
3. Model or method specification
4. Results
5. Interpretation and limitations

Avoid long explanatory sections when a short rule plus table is clearer.

## Keep Study-Specific Text Specific

Use concrete variable names, model formulas, sample labels, and data sources from the study at hand.

Bad:

> Various important covariates may influence outcomes and should be considered.

Better:

> Primary models adjust for `age`, `sex`, and `antibiotics_30d` as specified in the analysis plan.

## Do Not Invent Product-Like Copy

These are scientific reports, not landing pages. Avoid marketing tone, feature descriptions, and user-guide prose inside analysis reports.

Bad:

> Explore this interactive dashboard to discover meaningful trends.

Better:

> The table summarizes complete-case availability by exposure panel and outcome.

## Make Tables Readable

Use human-readable column names in rendered reports.

Bad:

```r
select(outcome_variable, outcome_family, non_missing_n)
```

Better:

```r
transmute(
  Variable = outcome_variable,
  Family = outcome_family,
  `Available, n` = non_missing_n
)
```

Small static tables should render as normal tables. Use interactive tables only when filtering or pagination helps.

## Preserve Useful Provenance

Keep comments or text that document real data decisions:

- manual duplicate-resolution lists
- known SPSS coding assumptions
- visit mappings
- derived-variable rules
- model/covariate decisions

Do not remove these just because they are comments.

## Final Check Before Rendering

Before rendering or sharing a report, scan for:

- useless comments
- analyst/person-name or lab-nickname references
- old copied study names
- TODO/FIXME placeholders
- meta-commentary about current work state
- AI-sounding filler
- table headers with underscores
- compact tables rendered with unnecessary search/pagination controls
